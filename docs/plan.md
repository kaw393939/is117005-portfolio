# Planning worksheet

Copy this structure into your own notes or repository. **This is a template, not a completed personal plan or a new course deadline.** Start with evidence; choose a small next step before coding.

## 1. Define the question

- **Goal:** What decision am I trying to make?
- **Scope:** Which role families, locations, and experience levels matter?
- **Constraints:** What time, budget, eligibility, or skill limits apply?
- **Done when:** What evidence would be enough to decide?

## 2. Compare the evidence

Use [job records](/jobs) as leads; recheck the employer's page before relying on availability.

| Record | What to capture |
| --- | --- |
| Source | Employer, exact title, URL, date checked. |
| Work | Main responsibilities and expected output. |
| Requirements | Required skills, preferred skills, experience, enrollment, and location. |
| Practical details | Pay range and unit, application deadline, work arrangement. Write “not stated” when absent. |
| Fit | Evidence I already have; gaps I need to address. |
| Confidence | What the source says versus my interpretation; questions to verify. |

Keep internship and full-time comparisons separate. A senior role can inform a long-term goal without being an immediate application target.

## 3. Choose a next step

Write a short decision note:

> I will explore **[direction]** because **[linked evidence]**. My main gap is **[skill or experience]**. I will produce **[small artifact]** to test **[question]**. I will reconsider if **[evidence or constraint changes]**.

Choose a [learning project](/pathways) only after you understand what it demonstrates. A useful report or experiment may be enough; not every question needs an application.

## 4. Plan a project before coding

If the next step is a software project, document these decisions first:

- **Scope and agile work:** user need, small user stories, acceptance criteria, tasks, and exclusions.
- **Technical architecture:** components, data flow, technology choices, alternatives, and tradeoffs.
- **Code structure:** responsibilities and interfaces; use SOLID principles and design patterns where they solve a stated problem.
- **Quality strategy:** fast unit checks, integration boundaries, a few critical end-to-end flows, linting, and static analysis.
- **Delivery:** setup, environment variables, test commands, deployment, risks, and rollback.

Keep the plan proportional to the project. Record unknowns and test them with a small experiment instead of writing a speculative design for everything.

## 5. Review, revise, and track

1. Have a partner review the sources and whether the information answers your question. AI can help; the reviewer still checks the result.
2. Open a GitHub issue describing the problem, the evidence, and what an improvement would look like.
3. Discuss the fix, make a focused change, and link the commit to the issue.
4. Verify the result before closing the issue.

Use a small action list: **action · evidence/link · owner · target date · status**. Set your own target dates; use Canvas for official course requirements.
