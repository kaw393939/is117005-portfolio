# Find your route into AI

Choose a problem you enjoy, build a small project, and use the results to decide what to explore next.

These are learning suggestions, not job guarantees. Compare responsibilities in the [career profiles](/careers), then read the [growth evidence](/research) before drawing conclusions about demand.

## Compare three starting routes

| Route | Questions you might enjoy | Foundations to practice | Bridge roles to investigate |
| --- | --- | --- | --- |
| **Build AI software** | How can an application use a model reliably? What happens when a request fails? | Programming, Git, APIs, testing, accessible interfaces, deployment | Software intern, junior developer, QA engineer, support engineer |
| **Work with data and research** | What does this dataset tell us? Does a model improve on a simple baseline? | Python, SQL, statistics, data cleaning, visualization, experiment design | Data analyst, research assistant, analytics intern, data engineering intern |
| **Secure and govern AI** | Who could be harmed? What should we test, document, or restrict? | Security basics, privacy, risk analysis, technical writing, model evaluation | Security analyst, QA analyst, compliance analyst, technology risk intern |

Bridge roles are search terms to investigate. Read each vacancy carefully: experience expectations vary. Research scientist roles can require substantial graduate training; a short project is not an equivalent qualification.

## Build a foundation you can demonstrate

Start with one programming language and Git. Practice explaining code, documenting data sources, and checking results with unfamiliar examples. Add SQL and statistics for data work; add HTTP, APIs, and deployment for application development.

Across all three routes, practice these habits:

- **Define the task.** State who needs the result and what success would look like.
- **Compare with a baseline.** Try a simple rule, search, or non-AI workflow first.
- **Test failures.** Include missing inputs, misleading results, and unexpected use.
- **Communicate limits.** Explain where the project works, where it fails, and what you would change.

## A four-week exploration plan

| Week | Focus | Something you can show |
| --- | --- | --- |
| **1 — Investigate** | Read three career profiles and compare five real vacancies. Record responsibilities, required skills, location, and experience level. | A dated comparison table with links and one route to explore. |
| **2 — Build** | Choose one project below. Define a small scope, collect suitable public or synthetic data, and create a baseline. | A working first version and a short project brief. |
| **3 — Evaluate** | Write test cases, measure results, inspect errors, and improve one weakness. | A repeatable evaluation and examples of failures. |
| **4 — Explain** | Clean the repository, check setup instructions, and write a reflection connecting your work to a career. | A readable README, demonstration, and next-step decision. |

Adjust the pace to your starting skills. Keep projects small enough to explain and evaluate.

## Three portfolio project briefs

### 1. A source-linked career information finder

**Explore:** AI application development and evaluation.

Build a searchable collection of a small set of public career documents. Begin with keyword search. An optional model-assisted answer should point back to the original source and decline questions the collection cannot answer.

**Done when:** documents have provenance; at least 15 questions have expected source references; unsupported questions receive an explicit limitation; keyboard navigation works; any credentials stay outside the repository.

**README evidence:** setup steps, architecture, baseline comparison, test questions, observed errors, and a screenshot or short demonstration. A search-only version is a valid first milestone.

### 2. A reproducible occupational growth notebook

**Explore:** data analysis and data science.

Use one clearly identified public employment projections release. Clean a small occupational table and create charts comparing percentage growth with the number of jobs added. Keep projection periods consistent.

**Done when:** raw and processed data are distinguished; calculations can be rerun; chart labels show geography and years; missing values are handled explicitly; conclusions distinguish projections from observed hiring.

**README evidence:** original dataset link, retrieval date, data dictionary, reproducible commands, findings, and limitations. Follow the site's [research method](/methodology).

### 3. An AI feature risk and evaluation report

**Explore:** AI security, governance, and quality assurance.

Choose a small fictional AI assistant and describe its intended users, data, and permissions. Use synthetic examples to examine unsupported claims, sensitive information, biased responses, and requests outside its intended scope.

**Done when:** the report includes a system diagram, risk register, at least 20 repeatable test cases, a severity rationale, and proposed mitigations with retest criteria. Keep testing within systems you own or are authorized to assess.

**README evidence:** scope, assumptions, test procedure, results, unresolved risks, and the boundary between measured behavior and your interpretation.

## Turn exploration into a decision

After finishing, write a short reflection: Which tasks held your attention? What evidence did you produce? Which skill blocked progress? Choose a next course, project, or vacancy search based on those answers, then revisit the [career profiles](/careers).
